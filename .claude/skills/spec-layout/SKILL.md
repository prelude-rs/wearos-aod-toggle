# Spec Layout (Authoritative)

This repository uses a change-based specification layout. **Skills are mandatory when they exist. This layout is not a suggestion — any artifact written outside this structure is a defect.** Announce that you are following `spec-layout` whenever you create or modify planning artifacts.

## Structure

```
CONTEXT.md                    # Domain glossary (term / definition / synonyms to avoid). See "Domain glossary".
docs/adr/                     # Architecture decisions that are neither state nor history. Born with the first ADR.
└── NNNN-<slug>.md            # 4-digit monotonic numbering, never reused. Format: templates/adr.md
specs/
├── SOURCE-OF-TRUTH.md        # Living system description. Rewritten by section at each sign-off (rule 5(b)).
├── epics/                    # Long-lived initiative specs (product-level WHAT + decomposition map + invariants)
│   ├── NNN-<name>.md         # Numbered: 001-data-lake-api.md, 002-sdd-adoption.md, … (see "Epic lifecycle")
│   └── LEGADO-NUMERACAO.md   # Only where old collisions exist: one declared pair per line (see "Epic lifecycle")
├── proposed/
│   └── <change-id>/          # A change still being discussed (until Gate 1.5). <change-id> = kebab-case, e.g. 2026-06-jwt-keycloak
│       ├── spec.md           # WHAT — requirements, scope, NFRs, out-of-scope. From templates/spec.md
│       ├── design.md         # HOW — stack, modeling, dependencies, trade-offs + the plan (## Decomposição, last section). From templates/design.md
│       └── consistency-report.md # Gate 1.5 findings. Form owned by the `consistency-gate` skill, section "Output". From templates/consistency-report.md
├── active/
│   └── <change-id>/          # A change in implementation: moved here by the design transcription at Gate 1.5 (fast-lane changes are born here)
│       ├── spec.md, design.md, consistency-report.md   # as approved, moved from proposed/ unchanged
│       ├── tasks.md          # Execution ledger, generated from design.md § Decomposição by check-tasks.sh --ledger. From templates/tasks.md
│       └── evidence.md       # Validation results. From templates/evidence.md
├── archive/
│   └── <YYYY-MM-DD>-<change-id>/   # Completed changes, moved verbatim
└── templates/                # Canonical templates. NEVER edit these during a change; copy them.
```

## Rules

1. **No implementation without an active change.** Code may only be written when `specs/active/<change-id>/` exists with `spec.md` and `design.md` marked `Status: Approved` **with an intact `approved-content` digest when the marker is present**, `tasks.md` present (the execution ledger generated from the design's `## Decomposição` — see "Status field"), **and `consistency-report.md` with `Verdict: PASS`** (the consistency-gate must have passed — Gate 1.5). The require-approved-spec hook enforces this. **The gate is per change, not per repo: while ANY folder in `specs/active/` lacks clearance, no code edit passes** — clear it (Gate 1.5) or archive it, and the block message names which folder and which condition. **A change still being discussed lives in `specs/proposed/<change-id>/`, not in `active/`, so it never blocks anyone's code:** the spec, the design and the consistency report are written there, and the design transcription (`! sdd-approve design`) moves the folder to `active/` as its last step, once the design is approved — `active/` means "in implementation". A folder never moves back: a Gate 1 reopening or a gate re-run after Gate 1.5 edits the artifacts where they are, in `active/`. Fast-lane changes are born in `active/`. **Known residual:** the gate cannot tell which change an edit belongs to; with a cleared change in `active/`, code for a change still in `proposed/` passes under that clearance. The doctrine holds it — only a change in `active/` is implemented — and review does; no hook does. A `Mode: fast` change is cleared by its signed `authorized-by` marker instead of the four tokens (see "Via rápida"). If asked to implement without these, STOP and run the spec flow first (see `spec-brainstorming`).
2. **One change, one folder, one deliverable — sized by the kind of work, not its count.** This rule is the *single owner* of sizing (the per-kind criterion and the number); every other surface refers here. **Kind (espécie):** an **epic** is several deliverables that share invariants — decompose it into changes (see "Epic lifecycle"); a **change** is one deliverable, with at least one design decision, that ends in a single green state — normally one autonomous session of agent work; the **via rápida** is work with no design decision — and choosing it is a human decision (see "Via rápida"). **Above 16 implementation tasks is an alarm, not a split order.** The alarm counts the `### Task N` blocks of `design.md`'s `## Decomposição` — implementation tasks only: the two mandatory closing rows of the ledger (run validation-gate; sign-off → archive) are not blocks and do not count — a ledger may reach 18 rows. Above 16 blocks, the design carries the labeled line `**Justificativa de dimensionamento:** <motivo>` between `## Decomposição` and the first `### Task N` block (the template puts it right under the heading), saying why the work is still one deliverable ending in one green state. `check-tasks.sh` asserts only its **presence** — absent, empty, or a placeholder fails the check (and so the design transcription); present, it emits an `AVISO … [dimensionamento]` line — and the consistency-gate judges its **merit** against the kind criterion above (check 6c). A justification that honestly describes more than one deliverable or more than one final green state means the work is an epic: split it by kind, never by count. **Atomic coupling caps the split the other way:** tasks that cannot *each* reach a green/verifiable state independently — where one's output breaks the build/suite until the other lands — must be planned as **one task**, not split. A task is one green commit-sized unit; splitting coupled work forces a red intermediate commit or an execution-time deviation. (Pilot: "move the config file" and "rewrite the loader to find it" had to be one commit — the move broke the loader until the rewrite landed.) **Change-vs-epic trigger (sizing decision):** by kind — a single deliverable ending in one green state is a **change**, whatever its block count (justified above 16); work that needs several deliverables, or shares invariants across several changes, is an **epic** to decompose (see "Epic lifecycle"). The "Epic lifecycle" section refers here rather than restating this.
3. **Delta specs only.** `spec.md` describes what *changes*, not the whole system. Reference `SOURCE-OF-TRUTH.md` and the relevant `specs/epics/NNN-*.md` for existing behavior instead of restating it.
4. **Epics are context, not flow participants.** Every `spec.md` must link its parent epic (if any) and list which epic invariants apply to it.
5. **Archive on completion.** When `evidence.md` shows all requirements validated: (a) move the folder to `specs/archive/<date>-<change-id>/`, (b) **rewrite the declared SoT sections — the single source for how `SOURCE-OF-TRUTH.md` is updated at sign-off.** The spec's `## Seções do SoT afetadas` (or `change.md`'s, in the via rápida) declares — by heading text, level 1–3; lines before the first heading belong to that first heading's section — which sections of `SOURCE-OF-TRUTH.md` the change alters, or carries `SOT-NO-DELTA: <motivo>` when it alters none. At sign-off, exactly those declared sections are **rewritten** from the requirements validated in `evidence.md` to describe the system **as it now is** — never append a paragraph narrating the change (SoT describes state, not history). `verify-archived-gates.sh` checks the archive in **both directions**: a section declared but left untouched, and a section touched but never declared, **both FAIL**, naming the heading and the direction (and the folder, on the declared-but-untouched side). A **removed** section is declared under the section that preceded it. **The SoT carries no `Status:` field and no approval transcription of its own — it is approved by the sign-off PR review** (this is the single source that closes epic 003 row H: no `/approve sot` subcommand exists or is needed). `sot-history-lint.sh` warns — never blocks — on transition wording left behind in the rewritten prose; a **provenance pointer** (the three forms defined in `spec-layout` → "Protocol tokens") is allowed inside a rewritten section. (c) note the archive path in the merge commit message, (d) **carry over** any unfinished or BLOCKED tasks into a new active change (or the parent epic's decomposition map) — work never disappears silently at archive, (e) **append one row to `specs/CHANGELOG.md`** (the change ledger — see `spec-layout` → "Change ledger"), **recording the parent epic in the `epic` column** (the epic-id, e.g. `002-sdd-adoption`, `—` if the change is standalone, or the literal `fast` if it was a fast-lane change — see "Via rápida"), **and, in the same step, one item under `## [Unreleased]` of the root `CHANGELOG.md`** (the release changelog; a release change declares its `seq` instead — see "Changelog de release"), (f) **if the change links a parent epic, stamp the backlink**: update that change's row in the epic's decomposition map so its status becomes `done → archive/<date>-<change-id>/`. Step (f) is **conditional** on there being a parent epic; it is what makes the epic a live board (rule 4 / "Epic lifecycle" closing check) — the cost is a **sync toll** (the epic file is edited once per child archive), accepted deliberately. The split is deliberate: **SOURCE-OF-TRUTH = current state, no history; CHANGELOG = history, no state.** **Closing debt is warned, never failed:** `.claude/hooks/check-closing-debt.sh`, delegated to by `verify-archived-gates.sh` on every PR, prints an `AVISO` for each change in `active/` that is concluded and not archived (evidence `COMPLETE`, or a fast-lane `change.md` `COMPLETE`), and for each folder in `proposed/` or `active/` with no commit for more than 30 days.
6. **Templates are read-only inputs.** Always start artifacts by copying from `specs/templates/`. Preserve every section; write `N/A — <reason>` rather than deleting a section. **Because that copy is mandatory, the templates are also where an execution lesson lives:** a rule learned the hard way goes into the instruction of the section it governs, so the next change reads it *by construction* instead of by remembering to open an archived `evidence.md` — the least-read artifact in the flow. A lesson that fits neither a template line nor a check **will not transfer**; say that instead of filing it somewhere that pretends otherwise.

## Status field

Every artifact carries a `Status:` line **except `tasks.md`**: `Draft` → `In Review` → `Approved` (spec.md, design.md) or `Pending` → `Complete` (evidence.md). **`tasks.md` has no artifact-level `Status:` and is not an approval artifact.** The plan is approved **inside** `design.md` at Gate 1.5: its `## Decomposição` (one `### Task N` block per task) is part of the design content the approval digest covers, and `.claude/hooks/check-tasks.sh <dir>` asserts the plan's **R*↔task coverage** before the gate is asked for. The ledger carries no artifact status because it is derived and changes during execution — `check-tasks.sh --ledger <dir>` generates it from the approved blocks, and its first `PENDING → DONE` would break any digest taken over it. The design transcription refuses when the coverage check fails: the launcher's `design` subcommand runs `check-tasks.sh` again and exits 4 without touching `Status:`. **Approval separates decision from transcription:** the *decision* to approve is always a human's, explicit, never inferred by the agent; the *transcription* is the human **typing `! sdd-approve <spec|design> [change-id]` at the prompt** (flips `Status:` + stamps an `approved-by` audit marker). **The `!` prefix is load-bearing, not decoration:** a `!`-prefixed command is a user shell escape and passes through **neither** PreToolUse hooks **nor** the auto-mode classifier — which is why it works where a slash-command's `` !`bash …` `` body did not (**measured: 1 success in 8 invocations, and the one success was not reproducible under an identical rule set**). `sdd-approve` is a launcher on the human's `PATH`, installed once per machine (see `INSTALL.md`); it resolves the installed plugin and always reports which path and version it ran. **The `[change-id]` is optional only while it is unambiguous:** with exactly one folder in `specs/active/` it auto-detects; with more than one it **refuses**, lists the active changes, and asks for the id. Because a PR delivers N changes (`git-practices` point 4), more than one active change is the *normal* case here — pass the change-id by default. The agent **never writes `Status: Approved`** and never invokes the launcher; its job is to *point the human to `! sdd-approve`*. This is an instruction, not an enforcement: no hook denies it, and the human's review of the PR is the control. **The human is never stuck:** the launcher is the preferred path (it stamps the `approved-by` audit marker), but the human may also **edit the `Status:` field by hand** — the hook only blocks the *agent*, never the human editing their own file (a hand edit just doesn't add the audit marker).

**Detail kept out of this file:** the verifiable `approved-content` digest (re-approval, removal read as divergence) and the design transcription that moves the folder from `specs/proposed/` to `specs/active/` (exit codes, the residual) live in `.claude/skills/spec-layout/references/status-field.md` — read it before touching either.

Individual tasks in `tasks.md` carry their own status: `PENDING` → `IN_PROGRESS` → `DONE`, or `BLOCKED` (with a reason). This is distinct from the artifact-level `Status:` above. A VISUAL task is `DONE` with green L1, like any other. The visual review is one per change that has a VISUAL task: when all tasks are `DONE` and before the validation-gate, the run pauses once, the app comes up by the design's Dev-run premise command, and the human operates it and decides; the approval is one transcription per change, typed by the human as `! sdd-approve visual [change-id]` (never by the agent). A rejection is a round recorded in `evidence.md` ("Visual checkpoints": items, fix commits, L1) — no task is reopened and the next review covers the whole change (see the `tasks.md` and `evidence.md` template doctrine).
