## The Superpowers encaixe (overrides SP skill defaults — read before brainstorming/planning)

When the Superpowers `brainstorming` and `writing-plans` skills run **in this project**, they MUST defer
to the kit layout.

1. **WHAT first, by us.** Run `spec-brainstorming` to produce `spec.md` and complete **Gate 1** BEFORE
   any HOW work. Do **not** run SP `brainstorming` before Gate 1 (it would double-question the user and
   can bypass the hook's spec-Approved requirement).
2. **SP `brainstorming` is the HOW engine.** Do not wait for it to trigger on its own:
   invoke it by name and enter it at *Lay out the approaches*. `spec.md` already holds the approved WHAT, so
   no WHAT question is asked (an echo of what you understood is fine). Two of its steps do not run:
   skip the builder check — the design's adversary is the consistency-gate;
   the design's size is always the kit template, not the SP's own sizing.
   Write its design to **`specs/proposed/<change-id>/design.md`**, using the kit's `design.md` template — NOT
   `docs/superpowers/specs/`, NOT SP's freeform layout. When the design needs an experiment,
   a spike is a throwaway clone outside the repo; what it taught enters the design as a measured prototype.
3. **SP `writing-plans`** writes the plan into the `## Decomposição` section of
   **`specs/proposed/<change-id>/design.md`**, before Gate 1.5, using the kit's `design.md` template: one
   `### Task N` block per task with its `**Refs:**` line (and `**Visual:** sim` when it changes UI
   surface) — the plan is approved with the design (spec-layout → "Status field"). The design also carries
   Global Constraints and Review Focus
   as sections before `## Decomposição`, never inside nor after;
   the plan review and the execution choice are answered at Gate 1.5.
4. **`subagent-driven-development`** executes the plan: it reads each `### Task N` block from the
   design (`task-brief design.md N`) and marks progress in the ledger `tasks.md`, generated by
   `check-tasks.sh --ledger`. Always name the model on every dispatch
   (omitting it inherits the most expensive tier); use the cheapest tier that fits the task. When all tasks are DONE and the
   plan has a VISUAL task, the run stops once for the visual review (`! sdd-approve visual [change-id]`),
   before the validation-gate — never per task.
   - **Mode:** execution is subagent-driven by default, or Native (`executing-plans`), chosen at Gate 1.5 and recorded in the `**Execução:**` line. Either mode reads the `### Task N` blocks of `design.md`, marks the ledger `tasks.md` (green L1 before DONE) and writes its rulings to `evidence.md` § Rulings.
   - **Rulings:** every `Ruling:` the run records is written to `evidence.md` § Rulings when it is made — the SP ledger is deleted at the end;
     a reviewer's out-of-spec judgment becomes a ruling there, never silent behaviour.
     The Confusion Protocol governs the WHAT/HOW interrogation; during execution, an ambiguity the spec and design leave open is a ruling, and one that would change a requirement is a stop — reopen Gate 1.
   - **Stops:** besides the SP's four, a fifth one —
     a kit hook or check that refuses the action, or a permission denial, blocked → stop and report; never a ruling around it.
     A hook or check message that names a fix to your own output (a commit subject over 72 characters, a red L1) is followed, never worked around.
   - **Green:** the per-task green is the project's `task-verify` L1; the full suite is L2.
   - **Workspace:** the SP workspace is scratch — what the gate, the visual review or the archive need never lives only there.
5. **`finishing-a-development-branch`**: choose the PR option; do the archive + SoT rewrite (rule 5(b)) +
   CHANGELOG bookkeeping (ledger row + release-changelog item — `spec-layout` → "Changelog de release") as
   the PR's commits. Never fast-merge to `dev` (PR-only).
   The end runs in this order:
   final review → visual review (if there is a VISUAL task) → validation-gate → sign-off → `finishing`.

## Idioma — pt-BR

**Instrução de maior prioridade: a equipe deste projeto trabalha em pt-BR.** Responda ao time em
**pt-BR** e escreva os **artefatos human-facing** em pt-BR — `spec.md`, `design.md`, `tasks.md`,
`evidence.md`, `consistency-report.md`, `SOURCE-OF-TRUTH.md`, o épico e o `CHANGELOG`. Não derive para o
inglês mesmo lendo skills/templates em inglês (eles são mecanismo, não o idioma da conversa).

Permanecem **em inglês/neutro** (nunca traduzir): os **tokens de protocolo** — o campo `Status:` e seus
valores (`Draft`/`In Review`/`Approved`), o campo `Verdict:` e seus valores (`PASS`/`FAIL`,
`COMPLETE`/`INCOMPLETE`) — os **IDs** de requisito/NFR (`R1`, `N1`), e **identificadores de código**
(símbolos, paths, flags, nomes de skill/hook). Esses são âncoras que os hooks e gates parseiam.
